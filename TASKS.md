- [x] Perform a second controlled reboot and collect monotonic kernel/systemd logs. This boot had an actual intermittent PCIe failure: `Speed change timeout`, link fallback to Gen1, no NVMe controller/partition enumerated by uptime 50s, and `/srv/data` mount dependency failed closed. Docker and Project Hub stayed stopped. Post-optimization cold-boot availability could not be measured on this attempt; existing data was not modified.
- [x] Read-only PCIe/NVMe diagnosis: compare the captured successful and failed boot traces, inspect the running kernel, active DTB, and Root Port state, and classify the failure. The captured successful trace enumerated endpoint `0000:01:00.0` (`1e0f:0001`, NVMe class), bound `nvme0`, found the expected partition/UUID, and mounted ext4 by monotonic 6.96s. The failed trace recorded `Speed change timeout`, Gen1 fallback, and no endpoint or `nvme0`; current Root Port state is Gen1 x1 but `DLActive-`/`DownstreamComp: Link Down - Present`, with no endpoint in PCI sysfs. Thus the observed failed boot is a link-training/link-active failure followed by enumeration failure; NVMe driver initialization is downstream and was not reached. Current retained journald no longer contains the early PCIe lines for either captured boot, so the exact normal/failure early-boot snippets are preserved here from the contemporaneous collection; do not infer that the retained journal can reproduce them.
- [x] Read-only platform configuration: kernel `6.6.98-sun60iw2 #1.0.2` (Debian 13 ARM64); active boot config points to `/boot/dtb-6.6.98-sun60iw2/allwinner/sun60i-a733-orangepi-zero3w.dtb`, SHA-256 `d0b9b052c6afcd64d1ac8e41c03b7dca11b007d62b72f0b6fb9b2b042fe78c1d`. Live and file DT both report `allwinner,sunxi-pcie-v300-rc`, `max-link-speed=<3>` (Gen3), `num-lanes=<1>`. Root Port `0000:00:00.0` reports max 8.0 GT/s x1, current 2.5 GT/s x1, `DLActive-`; no NVMe endpoint is enumerated. The active PCIe DT node has no `reset-gpios` or `power-gpios`; the captured failed-boot driver log warned these GPIO properties could not be obtained. Absence of those properties is evidence to investigate sequencing, not proof they are required or the cause.
- [x] Review public A733 reports without treating them as proof for this board. An Orange Pi 4 Pro community report describes a Gen3 speed-change issue with selected Phison drives and proposes changing its DTB `max-link-speed` to Gen1; its tested environment was kernel 5.15.147, not this Zero 3W/kernel 6.6.98 (https://github.com/CarterPerez-dev/orangepi-4-pro-nvme-fix). A Radxa A733 report describes a different case where an endpoint was already enumerated but its NVMe command/queues failed; that does not match this boot, which has no endpoint (https://github.com/radxa-build/radxa-a733/issues/10). Therefore Gen1 limiting is a plausible controlled experiment for a future authorized test, but is unproven here and must not be applied automatically.
- [ ] If authorized later, test Gen1 only as a controlled experiment on the active Zero 3W DTB above. `fdtput` and `fdtget` 1.7.2 are already installed. First confirm physical console/recovery access and that `/boot` is writable and has free space; create and hash-verify a metadata-preserving backup before changing exactly one property. Proposed commands (not run):

  sudo cp -a "$DTB" "$DTB.pre-gen1-20261011"
  sudo sha256sum "$DTB" "$DTB.pre-gen1-20261011"  # both must initially be d0b9b052c6afcd64d1ac8e41c03b7dca11b007d62b72f0b6fb9b2b042fe78c1d

  # Roll back before reboot if validation fails, or after a failed test:
  sudo cp -a "$DTB.pre-gen1-20261011" "$DTB"

  Only after the user's authorization, a validated edit, and confirmed recovery access would a controlled cold boot be considered. Capture early monotonic PCIe logs, `lspci -vv`, NVMe identity, mount UUID, Docker/Project Hub readiness, and database checksum. Risks: boot loss if the DTB is corrupted or the wrong file is edited; Gen1 x1 bandwidth reduction (2.5 GT/s raw, roughly 250 MB/s before protocol overhead); no guarantee if the cause is power/reset/connector/SSD. No DTB has been edited, and no reboot or rescan was performed for this diagnostic.
